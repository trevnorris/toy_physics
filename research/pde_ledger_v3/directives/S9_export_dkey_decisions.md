## The decision (user, 2026-08-08)

**A ledger key records the `D` at which the object was computed.**

Reason given: the bulk sector runs in 4D where the brane sector runs in 3D, and the flat ledger has one
slot per name. The next step (S10) sweeps `D ∈ {2,3,4,5}` in one run and will write one entry per `D`.
S9 is being re-keyed so that S10's `D = 3` results land on S9's keys and **overwrite** them. Without this
S10 overwrites nothing and the mechanism is untested.

## What to change

1. `scripts/S9_light_requires_shear_sympy_audit.py` — the export generator only.
2. `scripts/S9_exports.py` — regenerated by the run. Never hand-edited.

Nothing else. In particular: **do not touch the derivation, the action, the ansatz, the assumptions, any
computed value, or the `.wl` engine.**

- The engine's `.out` must be byte-identical to the committed
  `scripts/out/S9_light_requires_shear_sympy_audit.out` **except** for lines that carry an export key.
  Show the diff.

- `class`/`step` field semantics are unchanged; `step` stays `S9`.

## Three things measured on the current artifact — carry them into your directive

**1 · Free-symbol inspection does NOT determine whether an entry is D-dependent, and using it is the
obvious wrong implementation.** Measured: `transverse_multiplicity` has value `2` with no free symbols,
and it is the `D = 3` value of a quantity S10 computes as `1, 2, 3, 4` across `D = 2, 3, 4, 5`.
`lagrangian` and `equation_of_motion` likewise carry no `D` and are `D = 3` by their `t, x, y, z`
coordinates alone. A partition built from `free_symbols` will mis-key entries in both directions.

⇒ **The boundary is a fact about which code path produced the object, not about the value.** S9's
dimension solve produces objects symbolic in `D`; the ansatz/spectrum pipeline produces objects at a fixed
number of spatial components. The engine is the only thing that knows which; make it say so at the point
of production, and let the generator read that. **Do not infer it in the generator.**

**2 · S9 already implements this decision for four entries, under an ad-hoc convention.** `dim_solution`
and `dim_solution_d3` are both exported today, as are `dim_primary_inertia_d3`,
`dim_primary_stiffness_d3` and `dim_stiffness_minus_inertia_d3`. **Adopt the existing convention rather
than inventing a second one**, and make sure a mechanical suffix does not produce `dim_solution_d3_d3`.

**3 · The general-`D` entries must keep an unsuffixed key.** An object solved symbolically in `D` is not a
`D = 3` object and a later step does not overwrite it per-`D`. Decide and state in the directive what the
key shape is for that class, and apply it uniformly.
