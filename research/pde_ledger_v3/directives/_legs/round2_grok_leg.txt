## Blocking findings

### B1 · `P2` deletes the chain meeting `F1` requires (and re-runs v1’s D12 workaround)

**What is wrong.**  
`P2` maps `PY_S11_MAIN_D3_ROOT_ORDERING` → `s11_main_d3_root_ordering`. That embeds **step + package + D + quantity** in the storage key. `F1` (two-legged, settled) says keys stay **flat** and “a later step re-deriving that object writes **the same key**.” Putting `s11` in the key is a **producer/step prefix** by another name. The list’s distinction “engine prefix (D11) vs run-scope from §8 tags” is a rationalization: §8 is the **emission** grammar for dual-engine parity; S10’s actual ledger rule was `suffix.lower()` + optional `_dN` with `step` in the **row**, not the key.

**Mechanism — wrong physics survives.**  
After S11 “succeeds,” a consumer that still uses the S10 flat name reads **S10’s** spectrum:

```
flat_key_root_ordering_d3_after_S11= (0, mu_R*(k1**2 + k2**2 + k3**2)/rho_br)
flat_key_step= S10
p2_key_value= (mu_R*.../rho_br, B_comp*.../rho_br)
consumer_using_flat_name_sees_S10= True
```

(`/tmp/s11_review_P2_consumer_stdout.txt`)

Under `F1`+`F2`, writing flat `root_ordering_d3` would **meet** S10’s row, compare objects, and **fail loudly** (different objects — correct). Under `P2`, that measurement never runs; the under-specified name stays invisible; the merged ledger keeps S10 physics under the natural name.

**Same-object counterexample (chain, not S10∩S11 name list).**  
For S10→S11, M4 is right that the three flat name overlaps are **different** objects — so a flat key would not yield a quiet re-derivation, it would yield an F2 finding. The deleted measurement is:

1. **Future steps:** anything following the same rule writes `s12_…` / `s13_…` and can never share a key with S11’s objects.  
2. **D12:** the three collisions are exactly the open naming problem v1 was blocked for inventing a transform to route around. `P2` makes them unmeetable instead of measurable.

**Q6r under P2.**  
Still works on the **symbol-identity** population (`rho_br` → `inertia_coefficient_dimension`, `mu_R` → `stiffness_coefficient_dimension`). `B_comp` etc. correctly unresolved. Live lookups are not broken; the damage is the **tag-derived** namespace and stale flat derived names.

**Two populations under P2.**  
Disjoint: tag-derived keys are `s11_…`; no imported key starts with `s11_`. No silent self-overwrite between the two populations. That part of the list is true and insufficient.

**Vacuity of P4 on tag-derived vs import.**  
The list admits P2 makes tag-derived collision impossible. Confirmed: sample P2 keys ∩ imported = ∅. So F2 never fires on the M4 naming collisions. Vacuity operands make the dead guard *visible*; they do not restore the measurement.

**Third option (neither pure “ignore F1” nor P2).**  
Keep S10’s key rule: **quantity.lower() + `_dN` when D is integer; symbol-identity keys flat by `.name`.** On key present + different object → **loud F2 finding** (names both objects) and **do not write**. That *is* the D12 signal for `ROOT_ORDERING` / `DIM_*`. Do not invent a mechanical scope prefix to make divergence impossible (rule 6). Optional refinement: D12 renames the three under-specified objects so flat keys become honest — still not a producer prefix.

**What must become true instead.**  
Storage keys must remain meetable across steps for the same mathematical object (`F1`). Scope that is only emission grammar must not be copied into the ledger key. Collisions that are different objects must fail loudly (`F2`), not be defined away.

### B2 · `P5` is blind to non-value corruption of imported rows (including `dimension_key`)

**What is wrong.**  
`P5` compares only **values** between snapshot and output. `class`, `step`, `dimension_key`, `corroborated_steps`, `display`, `value_kind` can change freely.

**Mechanism.**  
Q6r (and any later consumer) resolves dimensions via `LEDGER[name]['dimension_key']` then `LEDGER[that]['value']`. Forging `dimension_key` on `rho_br` / `mu_R` retargets the imported dimension **without** changing the coefficient symbol value. Chain integrity residual stays empty.

**Literal output** (`/tmp/s11_review_P4_P5_guards_stdout.txt`):

```
# Accidental value write — P5 catches it
before_accident root_ordering_d3=(0, mu_R*(k1**2 + k2**2 + k3**2)/rho_br)
after_accident  root_ordering_d3=(999, mu_R*(k1**2 + k2**2 + k3**2)/rho_br)
P5_operand1_differing_imported_keys=['root_ordering_d3']
P5_operand3_symmetric_difference=['root_ordering_d3']
P5_detects_accident=True

# Metadata-only mutation — P5 does NOT catch it
metadata_only_mutation value_diff=[] residual=[]
P5_BLIND_TO_METADATA_MUTATION= True
```

**Defeat note:** if the accidental key is also placed in the “declared re-derives” set, residual empties again (`if_accident_also_declared residual=[]`). The list improves on v1 by saying “declared” rather than “touched,” but does not pin that the declaration is **a priori**, not “keys we wrote.” If a builder implements declared := written, v1’s tautology returns.

**What must become true instead.**  
Chain integrity must treat an imported **row** as the unit of identity (at least `value`, `class`, `step`, `dimension_key`, and any `corroborated_steps`), or emit separate residuals for each field — both operands and residual, per rule 2. Declaration of re-derived keys must be fixed before the write loop, not derived from it.

### N2 · No check that every non-`_LOCAL_` MAIN emission is present in the export

Downstream binds a missing key or keeps S10’s stale flat row.

**What must become true:** emit both the MAIN non-LOCAL tag set and the export key set (under whatever key rule survives), and their symmetric difference as residual — then guard.
